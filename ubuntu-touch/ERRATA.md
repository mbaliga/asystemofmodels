# ubuntu-touch ERRATA: spec defects and gaps met by the `ubuntu-touch-ut0` track, and the reading taken

Where a spec defect (`docs/design/mesh/REVIEW_ROUND3.md`, or one found while building) touches what this track implements, the
CONSERVATIVE reading was taken and is recorded here. Nothing was silently guessed. Ids are `ERR-UT-<area>-<n>`.

## ERR-UT-CLICK-2 (orchestrator, first hosted Clickable run 2026-09-30)

ERR-UT-CLICK-1 assumed Clickable substitutes `@APPARMOR_POLICY@` in the install directory. It does not: `clickable build` failed with "Failed reading .../install/asom.apparmor, it is not valid json", because Clickable parses the AppArmor file as JSON first. `asom.apparmor.in` keeps the placeholder and CMake `configure_file(@ONLY)` fills the policy version `2404.1` into the installed file (the value the framework `ubuntu-touch-24.04-1.x` maps to; Clickable rewrites it itself). `@CLICK_ARCH@` and `@CLICK_FRAMEWORK@` in the manifest and desktop file are unchanged. The static checks still accept the old placeholder form.

## ERR-UT-QML-1 (orchestrator, hosted runs 2026-09-30): the real Lomiri widgets need GL; the canary's review tool is behind the framework

- **QML tests.** `tst_StatusPage.qml` (the first test that creates the real Lomiri `Label` and `Button`) crashed natively (exit 139) under `QT_QUICK_BACKEND=software` on the offscreen platform. The hosted log of the follow-up run shows the same file passing 6 of 6 under `xvfb-run` with the default scene graph on Mesa software GL (`LIBGL_ALWAYS_SOFTWARE=1`) after the software-scene-graph run crashed. `tests/run_qml_ci.sh` now uses that configuration as its primary path (offscreen plus software scene graph only when `xvfb-run` is absent). Evidence: CI hosted container, not a device. Why the software scene graph crashes with these widgets was not investigated.
- **Canary (26.04-1.x).** The click builds; the image's `click-review` then fails with `'ubuntu-touch-26.04-1.x' is not a supported framework` and `Invalid framework` for the AppArmor manifest: the review tool in the canary image does not know the next framework yet. The canary job now builds with `clickable build --skip-review` and runs `clickable review` as an informational step (`continue-on-error`). A review that starts accepting the framework will show in that step's log.
- **AppArmor denials seen by the CI approximation (policy 2404.1 and 2404.2, self-test passed):** `/sys/kernel/mm/hugepages/`, `/sys/kernel/mm/transparent_hugepage/enabled`, `/proc/<pid>/coredump_filter` (JVM start-up probes) and `/proc/<pid>/net/if_inet6` (the JDK's IPv6 availability probe). None broke the self-test. `if_inet6` is the one to re-check on the device when the node starts enumerating interfaces for the mesh (UT-1): DV-UT item, owner-run.
