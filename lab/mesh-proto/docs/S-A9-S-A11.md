# S-A9 (TLS knob matrix) and S-A11 (SNI-token gating), JSSE on JDK 17 and JDK 21

Track `proto-tls`, LAB_SPEC work item L0.5 (TLS half). Evidence label: **LAB**, `oracle: self`. Measured with `./gradlew -p lab :mesh-proto:test` on Temurin **17.0.12** and OpenJDK **21.0.10** (Ubuntu build), Linux, loopback 127.0.0.1 only. **Not Windows, not Conscrypt, not Network.framework, not device evidence.** Every statement below is a measurement of those two builds; the rows are printed by the tests themselves (`S-A9 | ...` and `S-A11 | ...` lines in the test output) and the verbatim output is at the end. A table cell that says "yes" is backed by a handshake that tried to violate the knob and ended in a typed refusal on BOTH JDKs (test names given).

The scope column says where the setting lives: **engine** (`SSLEngine` / `SSLParameters` of one connection), **context** (the per-connection `SSLContext` and its managers). No JVM system property and no security property is set anywhere (design C12); `NoGlobalJsseStateTest` scans the sources and compares the JSSE properties before and after real handshakes.

## 2. Server tickets and resumption, the long form (R3-OVERCLAIM-6, R3-CLOSURE-7)

Question: can JSSE suppress TLS 1.3 tickets per `SSLContext` on JDK 17 and 21? **No on both** (measured: a shared listener context redeemed a ticket in the stock case, with `setSessionTimeout(1)` and `setSessionCacheSize(1)`, and with the server's session invalidated). What works is not sharing the context: the listener builds a fresh `SSLContext` for every accepted connection, so a ticket from an earlier connection finds no key to open it and the server ignores the PSK and runs a full handshake with client authentication. Result per lane: JDK 17.0.12 refuses resumption, JDK 21.0.10 refuses resumption; the lender security claim rests on the per-connection context in `MeshTls.establish`, not on the JDK version. Mutants M04a and M20 (a shared context) are killed by the suite on both JDKs.

## 3. S-A11: SNI-token gating through `X509ExtendedKeyManager` (design T13)

Experiment (`SniGatingSpikeTest`, `SniGatedKeyManager`, test sources only): the dialler puts `trunc64(HMAC-SHA256(pairKey, epochHour))` as a base32 label under `.invalid` in `SSLParameters.serverNames`; the listener's key manager reads `ExtendedSSLSession.getRequestedServerNames()` of the handshake session inside `chooseEngineServerAlias` and returns no alias unless the label is the current hour's token.

| Case | JDK 17.0.12 | JDK 21.0.10 |
|---|---|---|
| right token | decision `granted`, the dialler checked one certificate, 3365 listener bytes | same, 3353 listener bytes |
| no SNI | denied; the dialler checked 0 certificates and learned no pin; 344 listener bytes (ServerHello and alert); alert `handshake_failure` | same, 334 bytes |
| a token under another pair key | denied, no certificate, 344 bytes | denied, no certificate, 334 bytes |
| last hour's token | denied, no certificate, 344 bytes | denied, no certificate, 334 bytes |
| token replayed from a captured ClientHello, same hour | accepted (established) | accepted (established) |
| a label with no dot, set explicitly | sent on the wire, compared like any other name | same |

**Verdict: works with caveats, on both JDKs.** The certificate (and so the pin) is withheld from anyone without the token, and the key manager can do it. Caveats: (1) the token travels in clear in the ClientHello, so a passive observer can replay it for the hour (as T13 already says); (2) the key manager is asked once per key type (four times for a denial), so the decision must be idempotent; (3) the listener still answers with a ServerHello and an alert, so a prober learns that a TLS 1.3 server is listening; (4) the dialler must put its peer in `serverNames`, which the mesh profile deliberately does not do today; (5) Conscrypt and Network.framework are **UNVERIFIED**. NOT enabled in the profile: the default stays no SNI (ERRATA ERR-PL-14). The ALPN gate of section 1 already withholds the certificate from a dialler that does not offer `asom-mesh/1`, which is less than this and costs nothing.
